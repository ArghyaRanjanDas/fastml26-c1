## ACTION BRIEF — Challenge 1, final 24h

Four lanes run in parallel. Nothing blocks anything else.

---

### LANE 1 — synthesis-box: da4ml resynthesis of the current checkpoint
Owner: synthesis-box. Effort: 30 min setup + long background run.

1. `python -m venv ~/venv-da && source ~/venv-da/bin/activate && pip install 'hls4ml[da]'`. Verify `import da4ml`, `hls4ml.__version__ >= 1.3.0`. Do NOT touch the existing QKeras env.
2. **First**: finish and record the pending non-DA `ap_fixed<16,6>`/AP_SAT LUT/FF/DSP numbers. Without that baseline the DA delta is unmeasurable.
3. Dump the current per-layer `ReuseFactor` from the working config and confirm it is already 1. If any layer has RF>1, flag it — setting RF=1 is then a resource change, not a no-op.
4. Set `Strategy='distributed_arithmetic'` and `ReuseFactor=1` on every Dense layer. Backend Vitis, part xcu200, 5 ns clock.
5. `hls_model.compile()`, run the 100k eval set, confirm AUC matches the fixed-point AUC to ~1e-4. DA ignores the accumulator precision setting, so this check is mandatory.
6. Fast checkpoint: `build(csim=False, synth=True, vsynth=False)` → HLS-estimate LUT/DSP within ~1.5 h. Then launch `vsynth=True` as a **background** job (comparable published runs took ~17 h; do not gate anything on it).

Success: DSP drops from 1,724 toward ~0 at unchanged AUC. LUT savings are architecture-dependent — for a narrow net like ours expect single-digit to ~25%, not 30-50%. Beat: 1,724 DSP / 319k LUT.
Abort: any layer unsupported → revert that layer to `Strategy='Latency'`, record which, continue. If AUC shifts >1e-3, stop and report — do not synthesize.

### LANE 2 — student-GPU (A100): HGQ2 QAT with distillation on
Owner: student-GPU. Effort: 7-8 h (raised from 5; the assumed template does not exist).

1. `python -m venv ~/venv-hgq && pip install 'hls4ml[hgq2]'`. Keras v2 and v3 cannot coexist — leave the QKeras env alone.
2. **Do not** start from `small_jet_tagger.ipynb` — it is a flat 28-feature MLP with no per-particle or pooling structure. Use `calad0i/JEDI-linear` as the per-particle template, and hunt for the DeepSets+HGQ training code behind Table 1 of arXiv:2510.24784 (stated to live in the HGQ/hls4ml packages). Budget time to locate and adapt it.
3. **Toy-model gate (30-45 min, before full training):** build a 2-layer mean-pool + concat DeepSet in `hgq.layers`, push it through `convert_from_keras_model`. Confirm the pool and concat survive as trivial ops (tutorial slide 23 multiplication check). If the pool breaks conversion, stop and report before spending GPU hours.
4. Rebuild the student: QDense phi 32-16-8 over the candidate axis, mean-pool (N=16 → exact >>4), concat the 11 quantized event scalars, QDense rho 32-16-1.
5. Config scopes verbatim from the FastML26 tutorial slide 19: `SAT_SYM` on `place='all'`, `kif`/`WRAP` on `place='datalane'`, `enable_ebops=True`, `beta0=1e-5`. Train with `KERAS_BACKEND=jax`, `jit_compile=True`, warm-start from the float checkpoint, ramp beta with `BetaScheduler`.
6. Keep KL(T=2-4)+BCE distillation ON throughout. Do not run float → distill → quantize as three stages.
7. Run the post-training calibration pass on held-out data (WRAP datalane requires it).
8. Sweep beta0 {1e-6, 1e-5, 1e-4}; pick the operating point from the training-time EBOPs readout before touching the synthesis box.
9. Convert with no manual precision config, `Strategy='distributed_arithmetic'`, RF=1.

Success: AUC ≥ 0.881 at materially lower LUT/DSP than 319k/1,724. Treat the published 3.6x LUT / 2.2x latency figures as directional (different papers, different training budgets, XCU250 not XCU200), not as a promise.
Abort: if step 3 fails, or if QAT has not reached AUC ≥ 0.875 by hour 5, fall back and ship the PTQ `ap_fixed<16,6>` model.

### LANE 3 — student-GPU (A10): JEDI-linear global-context term
Owner: student-GPU, second card. Effort: 4 h **only** as a plain-hls4ml edit.

1. Compute `c = mean_j(x_j)` over the fixed 16-slot zero-padded array (exact >>4; divide by 16, never by n_cand — no divider).
2. Feed phi as `W1*x_i + W2*c + b`, two weight matrices. Do **not** implement as `concat(x_i, c)` into a 10-input phi — `W2*c` must be evaluated once per event, that is the entire resource argument.
3. Implement with ordinary hls4ml layers (Dense + GlobalAveragePooling1D + Add) inside the **existing** PTQ/QAT + Vitis flow. Do not stand up HGQ2/da4ml for this lane — the paper's 0-DSP/147k-LUT numbers come from its bespoke Verilog backend, not from Vitis HLS, and are not our expected numbers.
4. Train in the existing distillation loop.
5. Variant B only if round one holds: broadcast the pooled 8-vector back, concat per candidate, phi2 (8-8), pool, rho. ~500-1000 extra params.

Success: **ttbar-only AUC above 0.759.** A full-AUC wash with a ttbar gain still ships.
Abort: ttbar AUC does not move, or the change costs >2 h of debugging. The paper's own DeepSet-vs-JEDI-linear comparison at matched N is a wash (66.5 vs 65.1-66.6) — expect near-noise, treat as a cheap speculative try. If it needs HGQ2 infra to work, drop it.

### LANE 4 — physics-CPU: dxy order statistics + BDT diagnostic
Owner: physics-CPU. Effort: 3-4 h total, fully parallel.

1. (45-60 min) Add the 2nd, 3rd and 4th largest |dxy| among the 16 candidates as three extra event scalars. HH→4b has four b-hadrons, ttbar has two; a dxy *sum* cannot separate few-very-displaced from many-mildly-displaced, an order statistic can. Hardware cost is a comparator network: 0 DSP. Note hls4ml has no built-in top-k — this is a small hand-written pre-processing block.
2. (15 min, gate) Before any HLS work on pairing: numpy-only diagnostic. Take the leading-4 candidates, form the 3 pairings, minimize ATLAS D_HH, plot m_H1 for signal vs each background. If no signal enhancement appears, the pairing idea is dead — stop there. Expect it to fail: our inputs are *particle-flow candidates*, not clustered jets, so two of the leading four can easily come from the same jet.
3. (2 h) Two BDTs on the CPU box: (a) **11 event scalars only** — this is the clean diagnostic; (b) scalars + candidate aggregates + the new dxy order statistics. Report overall AUC *and* the QCD/ttbar/W+jets breakdown against 0.930/0.759/0.972.
4. Read the diagnostic: scalars-only near 0.887 → the bottleneck is feature content, pour hours into features. Far below → representational, hours belong in Lanes 2-3.
5. `pip install conifer`, convert, synthesize — but **only after** the DeepSet job clears the Vitis queue. For binary (not 5-class) at depth-4/100-trees expect ~19k LUT (~1.6% VU9P), 0 DSP, ~60 ns.

Success: step 1 ships if ttbar AUC moves at all (it is free). Step 3's value is the diagnostic answer, delivered by hour 3.
Abort: step 2 diagnostic shows no mass structure → drop pairing entirely, no HLS time. The BDT is **not** a submission candidate — we already have a synthesized in-budget fallback at AUC 0.883.

### DO NOT BOTHER

- **X_HH / D_HH dijet pairing in firmware**, unless the 15-min numpy diagnostic passes. Candidates are not jets; the asymmetry feature needs an unbudgeted divider, and the ap_fixed<22,10> config is already at 91% DSP.
- **Feature-matching / FitNets projector, RKD, and reliability weighting (JetCoRD).** The closest HEP precedent gives +0.0011 AUC — below our own 0.002 noise floor. Do the 30-min BigDeepSet-as-teacher swap (TAKD) as a one-line regression check; if that alone does not clear +0.004, stop. Never debug a new loss term inside an unproven QAT loop.
- **A reuse-factor sweep.** Mutually exclusive with da4ml (RF must be 1), and Lane 1 dominates it.
- **BDT-DeepSet logit ensemble.** No cited evidence naive averaging with a weaker model helps AUC; it likely hurts uncalibrated.
- **Any O(N²) relational block** — mini edge-MLP, pairwise features, full interaction network. We do not have the DSPs.
- **Chasing LUT reduction as the headline DA win.** DSP→0 is the robust effect; LUT savings on a narrow net are marginal.

## Skeptic verdicts
- **da4ml distributed-arithmetic resynthesis of the existing checkpoint (no retraining)** — REFUTED: Checked all four angles against primary sources (hls4ml da.html docs, da4ml paper arXiv:2507.04535 full text incl. Tables 3-13, and the search-derived context on the Alkaid backend).

Verified accurate: the docs quote "DA can usually reduce up to 30% of the LUTs and all DSPs used," the RF=1-for-CMVM requirement, the "accumulator precision setting will not be used"/bit-exact claim, the hls4ml[da] install path, and Dense-layer support — all match the live docs verbatim. The API usage (Strategy='distributed_arithmetic') matches the paper's own Listing 1. AUC-safety is real: DA is bit-exact to the fixed-point spec, so the recipe's near-zero-AUC-change claim is correct and the ~1e-4 sanity check is the right safeguard, not a weakness.

Two load-bearing claims fail on inspection:

(1) LUT reduction is oversold for this architecture. The paper's own realistic-network tables (5-9) show LUT gains ranging from ~6% (Muon Tracking net, widths 8-14-28-50, all-Dense — the closest fan-in analog to this DeepSet's phi-net fan-in of 5 and rho-net fan-in of 19) up to ~25% (SVHN CNN, much wider fan-in), never near 30%, and the authors explicitly describe the narrow-network case as yielding only "marginal" LUT savings. The cited "-50% Alkaid" figure belongs to a separate RTL-direct backend that is 5-20% better than the hls4ml+da4ml HLS-C++ path (per the same slide deck's source material) — i.e. a different implementation than what the recipe's step 3 (backend='Vitis') actually exercises. DSP→~0 is however robustly evidenced across every real-network table regardless of width, so that half of the "expected_effect" stands.

(2) The 1.5-hour / "report back within the hour" timeline is not credible for step 5 (full vsynth=True). The da4ml paper itself states that Vitis-HLS+Vivado synthesis of a 137k-LUT realistic network (smaller than the hackathon's already-reported 319k-LUT/1724-DSP baseline, on a smaller VU13P part vs the target xcu200) took "around 17 hours" via this exact hls4ml+da4ml HLS route (vs. 26 minutes only via the RTL-direct route this recipe doesn't use). Given the hackathon model is larger, a full vsynth run plausibly takes hours, not 1.5, which would blow the ~24-hour clock if treated as a same-hour gating task for recipe #2.

Given the numeric core of the proposal (30-50% LUT cut, solved-in-an-hour) is contradicted by the cited paper's own data on architecturally similar networks, while only the DSP-elimination claim and AUC-safety claim survive, this is refuted as stated — though it is a partial refutation: the underlying method is real and DSP-elimination is a genuine, well-evidenced, low-risk win worth pursuing with the adjusted expectations and timeline in `fix`.
- **HGQ2 per-parameter QAT with the distillation loss active, exported through da4ml** — survived: Every hard number the recipe quotes checks out under direct verification: Table 1 of arXiv:2510.24784 gives exactly 70.1%/53ns/205k LUT/0 DSP (HGQ) vs 69.4%/115ns/747k LUT/555 DSP (QKeras) at 16 particles, and the FastML26 tutorial slides reproduce the config-scope code, BetaScheduler API, calibration-pass warning, and jax-backend guidance verbatim. hls4ml[hgq2] is a real PyPI extra. So the evidence is not weak or fabricated. However two concrete, verifiable flaws survive: (1) the cited starting example, example/small_jet_tagger.ipynb, is a flat 28-feature MLP with no per-particle layer, pooling, or concat — it is not 'the same class of model as ours' as claimed, so the 5-hour effort estimate rests on a template that doesn't exist as described, and no accessible public example of HGQ2 applied to a DeepSets-shaped (per-candidate MLP + pool + concat) architecture could be confirmed, only the Table-1 result itself (produced by the tool's own authors, code not located); (2) the 'verified apples-to-apples' framing overclaims — the HGQ-DeepSets and QKeras-DeepSets rows being compared are different architectures from different papers under different training budgets (XCU250, 350k EBOPs target for one; independently-sized model for the other), not a controlled ablation isolating quantization method, so the specific 3.6x LUT / 2.2x latency multipliers are not guaranteed to transfer to our 5-feature-per-candidate, event-scalar-augmented, binary-task student. The mean-pool-as-'trivial-op' claim is asserted rather than demonstrated, against the tutorial's own explicit warning to check for multiplication before trusting automatic conversion. The arXiv:2311.14160 citation for 'KD-during-quantization' is also not supported by its abstract, which never mentions quantization. None of this undermines the core mechanism (HGQ2 QAT with distillation loss active, exported through da4ml, targeting a comfortable single-SLR fit at parity-or-better AUC) — FPGA/latency feasibility is comfortable given the huge margin under 1us, and the modest AUC claim (parity-or-better vs current 0.881-0.883 PTQ) is plausible and clears the ~0.002 noise floor either way. This is a partly-wrong recipe with a fixable premise error, not a refuted proposal.
- **JEDI-linear global-context term: relational information at O(N) cost** — REFUTED: Read arXiv:2508.15468 directly (PDF pages 1-8, including Table I/II, Fig.4, Eq.1-4, Sec.IV-C) to check the four requested angles.

(1) Applicability to 16x5, ~2k params: PARTIAL. Particle counts N=8/16 are directly tested (good — the O(N) vs O(N^2) collapse in Eq.3-4 is algebra, not an empirical fit, so it's scale-robust regardless of N). But feature count is not: the paper only tests P=3 (pt,eta,phi) or P=16 (the full JEDI-net kinematic set), and going P=3->P=16 at N=16 moves accuracy 73.75%->78.3%, a large feature-driven swing — so no data point brackets our P=5 closely enough to extrapolate an accuracy number, and the proposal correctly avoids promising one but the "why_ranked_here" framing still implies more confidence than that gap supports. Parameter count is unvalidated: paper never reports param counts, and its smallest configs already synthesize to 38k-147k LUT — same order as our ALREADY-SYNTHESIZED 2,041-param DeepSet (319k LUT, pre-QAT) — so nothing here confirms the JEDI-linear mechanism stays cheap at ~2k params specifically. Bigger issue: the paper's task is 5-way OFFLINE jet-substructure tagging (single jet, up to 128 constituents) vs our binary ONLINE event classification (16 leading PUPPI candidates spanning the whole event, HH4b's two-Higgs bimodal topology vs ttbar's trimodal one) — a domain gap the recipe doesn't engage with, and it lands squarely on the diagnosed bottleneck class.

(2) 4 agent-hours: OPTIMISTIC AS WRITTEN. The recipe tells the agent to "copy model-definition patterns from JEDI-linear, already written in HGQ2" and train "inside the same distillation+HGQ QAT loop," but the paper explicitly uses a Keras+da4ml pipeline that generates Verilog directly, stating in Sec.IV-C that its fully-unrolled architecture "cannot be efficiently handled by existing HLS compilers due to large loop bounds and structural complexity" — i.e. NOT the hls4ml/Vitis-HLS path our context specifies as required. If the agent actually stands up HGQ2+da4ml as literally instructed, that's new infrastructure, not a 4h task. It's only ~4h if bolted onto the team's already-working PTQ/(soon-QAT)+hls4ml+Vitis pipeline as plain Dense/GlobalAveragePooling1D layers instead.

(3) FPGA/latency feasibility: WEAKENED BY THE PAPER'S OWN TEXT. The proposal's "expected_effect" cites Table I's 0 DSP / 147k LUT / 79ns for JEDI-linear at 32 particles — but those numbers come from da4ml's multiplier-free distributed-arithmetic Verilog generation, a toolchain the paper says exists specifically BECAUSE standard HLS compilers can't handle this structure efficiently. Under the hackathon's mandated hls4ml+Vitis HLS 2024.1, expect materially worse numbers (more DSPs, more LUTs) than Table I — those numbers are not evidence for what our synthesis box will produce.

(4) Gain vs ~0.002 AUC noise: NOT SUPPORTED. Table I reports 5-way top-1 accuracy on an unrelated task, not AUC on ours — the proposal concedes no HH4b number can be promised, which is honest, but the paper's own most relevant same-N ablation (JEDI-linear vs "DS" DeepSets baseline, N=8/P=3: 66.5% vs 65.1-66.6%) is close to a wash, not the dramatic win implied by comparing against the O(N^2) GNN-J5 baseline in the "expected_effect" field. Since our student is already a DeepSet (not a full-pairwise GNN), that GNN-J5 comparison is the wrong reference class for us, and the right reference class shows a gain that could plausibly sit inside the noise floor.

Net: the core algebraic mechanism (Eq.2-4, verified accurate as quoted) is legitimate and nearly free to bolt onto an already-O(N) DeepSet, and the ttbar-only gate is sound risk management — but the recipe's evidentiary case leans on a mismatched baseline (O(N^2) GNN, not DeepSets), a toolchain the paper itself says is needed because HLS compilers don't handle this well (contradicting the hackathon's Vitis-HLS requirement), and an optimistic effort estimate that assumes infra (HGQ2/da4ml) not established in the given context. Per the default-to-refuted rule, these gaps are enough to refute the proposal as written; it survives only with the reframing in `fix`.
- **Distillation upgrade: BigDeepSet as teacher-assistant plus discardable feature-matching projector** — REFUTED: Verified all four load-bearing citations by fetching the actual papers/abstracts rather than trusting the proposal's characterization.

(1) Domain/architecture fit is weak. TAKD (Mirzadeh et al.) and FitNets (Romero et al.) are CNN/image-classification results (CIFAR-scale networks, intermediate conv feature-map hints) with no permutation-invariant-set or HEP precedent; extrapolating "large capacity gap stalls KD, TA/hints fix it" to a 16-item, 5-feature DeepSet with an 8-dim pooled bottleneck and a 2,041-param budget is an unverified cross-domain leap. The one genuinely comparable HEP citation, arXiv:2311.14160 (LorentzNet→DeepSet KD), uses full jet constituents (variable multiplicity, 4 features: pT, eta, phi, mass — no event-level scalars, no dxy) on a top-tagging task, not L1-trigger PUPPI candidates with 11 auxiliary event features — a materially different input structure.

(2) The proposal's own cited "closest HEP precedent" undercuts its numeric claim rather than supporting it. I fetched the paper's actual numbers: teacher 224k params, student 68.2k params (only a 3.3x gap — a favorable, non-TAKD-triggering regime), and vanilla logit KD moved AUC by only 0.9808→0.9819, i.e. +0.0011 absolute. That is *smaller than this team's own stated 0.002 AUC noise floor*, and it used no feature-matching or RKD — just KL+CE. The proposal cites this exact number and then claims a "realistic expectation +0.003 to +0.01," a range whose floor is already ~3x larger than what its own best evidence shows, with no other citation offered for the extra magnitude. That gap is not defensible.

(3) Stage D's citation (JetCoRD, arXiv:2607.15531) is honestly flagged as unreplicated by the proposal, but I fetched its ablation table and it is *worse* than the proposal implies: vanilla-KD baseline moves background margin by -0.04%, and the full reliability-aware pipeline (gate + prototype repair + weighting, never isolated) moves it by only +0.22-0.40%. There is no ablation isolating "reliability weighting alone," so it provides no real evidentiary support for Stage D's claimed benefit, and the paper's actual motivation (reconciling two structurally different real cross-experiment teachers) doesn't match a single, well-calibrated float teacher.

(4) The team's own already-measured analog (ParT-lite logit KD: 0.887→0.890, +0.003) sits right at the edge of the stated noise floor. Chasing further fractions of that already-marginal effect through 3.5 more hours of stacked hint-matching, RKD, and reliability weighting — run inside an as-yet-unvalidated HGQ QAT loop rather than validated in float first — risks consuming scarce hours for a change that both the team's own prior result and the best-matching published precedent say is likely to land inside measurement noise, not the claimed +0.003 to +0.01.

The one part of the proposal that is genuinely sound and should be kept: discarding the projector P before hls4ml conversion means the architecture is byte-identical to the shipped 2,041-param model, so there is truly zero FPGA/latency cost regardless of the training-side gain. That claim holds and is not part of the refutation.
- **Two physics features aimed straight at ttbar: |dxy| order statistics and X_HH-style dijet pairing** — REFUTED: Attacking on all four requested axes:

(1) Evidence transfer to our inputs — this is where the proposal breaks. arXiv:2301.03212 is confirmed real (ATLAS nonresonant HH→bbbb, PRD 108, 052003) and the D_HH/X_HH-style resolved pairing is a real, standard ATLAS technique (confirmed by search; a closely analogous CMS diagonal-distance pairing d_HH=|m_H1-α·m_H2|/√(1+α²) also exists in the literature). But that technique is applied to calibrated, individually-clustered, b-tagged offline JETS — objects that already aggregate all the particles from one parton. Our "16 leading L1 PUPPI candidates" are individual particle-flow-level objects (the presence of a per-candidate dxy, which is only meaningful for a track/charged particle, confirms this), ranked by pt across the WHOLE EVENT with no jet-clustering step anywhere in the given inputs or the recipe. A typical R=0.4 jet has many charged+neutral constituents, so it is entirely plausible — likely, for a hard leading jet — that 2 or more of the "leading 4 candidates" originate from the SAME jet (e.g. its leading charged hadron and leading photon), especially in QCD background events dominated by one very hard jet. "Pairing candidates 1-4 into dijets" is then not pairing 4 b-jets, it's an arbitrary mix of same-jet and cross-jet particle pairs, and the resulting m_H1/m_H2 will generally NOT cluster near a Higgs-mass-like region the way true dijet masses do. The recipe cites the MIT thesis (dspace 1721.1/151433) for L1 dxy b-tagging feasibility, but that thesis explicitly builds seeded-cone JETS from PUPPI candidates first and only then runs a per-jet tagger on that jet's own constituents — a materially different (and more expensive) architecture than "pair the top-4 event-wide candidates," so that citation does not actually support the pairing recipe as written, only the general idea that dxy carries b-tagging information (which supports half 1, not half 2). This is a mechanism failure, not merely an "unverified magnitude" as the proposal itself hedges — it's a reasonable prior that the pairing signal is weak-to-absent at this granularity, not just unmeasured.

(2) Agent-hours — the dxy order-statistics half (45 min) is plausible, if optimistic once retraining/eval cycles on 2M events are included. The pairing half's 1.5h is optimistic once you count: defining the 3 pairings, the D_HH argmin logic, handling n_cand<4 zero-padding (unaddressed — candidates 3/4 can be padding, silently producing garbage "Higgs candidate" masses for a nontrivial fraction of events), retraining/eval, and (per the fix above) a diagnostic that should have been step 1 but isn't in the recipe. Total 3h is roughly consistent with the stated sub-steps only if nothing goes wrong, which is unlikely for a novel HLS block with no hls4ml-native support.

(3) FPGA/latency feasibility — the "0 DSP" claim for the sort is right and cheap to implement (comparator network), but it must be hand-coded as a custom pre-processing block since hls4ml has no built-in top-k/sort layer — a real, uncosted integration task. For the pairing half, the resource claim ("n_new × 32 extra MACs") only counts consuming the new features in rho — it ignores computing them: ~9-12 multiplies (DSPs) across 3 pairings for the mass terms, a cosh(Δη) LUT that needs real range/precision engineering (Δη can reach ~5, cosh(5)≈74, combined with wide-range log-pt inputs), argmin/branch logic, and critically a DIVISION for the asymmetry feature — divisions are among the most expensive HLS primitives (multi-cycle or heavy LUT/DSP use for a reciprocal approximation) and are completely unbudgeted here. This lands on top of a DSP budget that is already ~91% consumed (1724/1900) in the currently-synthesized ap_fixed<22,10> variant per the given context — there may be no room left at all in that configuration, and the proposal doesn't even name which fixed-point variant would host the new block.

(4) Gain vs. noise floor (~0.002 AUC) — the proposal itself admits "magnitude unverified... no paper gives an AUC delta at L1 granularity," which combined with the mechanism problem in (1) makes a positive gain speculative rather than merely unmeasured. It's further undercut by a point the proposal misses: the given 11 event scalars already include m2 and m4 (invariant masses) and "dxy sums" — so some of the claimed "genuinely new information" (total mass scale, aggregate displacement) is likely already partially available to the tiny 2k-param student, shrinking the marginal value of the pairing features specifically. The dxy order-statistic half is comparatively more defensible against this axis since order statistics are demonstrably non-redundant with a sum, and its cost is low enough that even a modest, uncertain gain is worth taking.

Net: the proposal is only half right. Default-refuting the bundled proposal as stated because its headline, most-expensive, most-novel claim (the X_HH pairing) rests on a jets-vs-particle-candidates evidence mismatch, has understated FPGA cost against an already near-saturated DSP budget, and has an admittedly unverified AUC effect that a cheap diagnostic should have screened for before any implementation hours were spent. The dxy order-statistics half should survive as a cheap, low-risk addition.
- **conifer BDT as bottleneck diagnostic, near-zero-cost fallback, and optional ensemble** — REFUTED: Verified against primary sources this session. The FPGA-cost evidence itself checks out well: arXiv:2002.02534 (fetched full text, Table 1 / Fig.4 / Sec.3.3) confirms verbatim "inference latency for this ensemble is 12 clock cycles, corresponding to 60 ns" and Table 1 gives 96,148 LUT (8.1% of VU9P), 0 DSP, 0 BRAM for a 100-tree depth-4 BDT — and since that benchmark is 5-class (5 trees/estimator) while ours is binary, our expected cost is actually ~1/5 of that (~1.6% LUT), even better than the proposal claims. Feature count (11-30 for us vs 16 in the paper) doesn't materially change this since HLS unrolls one comparison per node regardless of total feature count, so criterion (3) FPGA/latency feasibility is NOT refuted — if anything the recipe undersold the headroom. But four other things are wrong: (a) the citation "Aarrestad et al., arXiv:2104.03408" is a verification failure — that paper is by Hong, Carlson, Eubanks, Racz, Roche, Stelzer & Stumpp (fwXmachina), not Aarrestad; content is still roughly on-topic but the sourcing was not actually checked. (b) The "insurance policy" pitch is weak: the team already HAS a synthesized, in-budget model (ap_fixed<22,10>: 0.883 AUC, 319k LUT/1724 DSP, 0.39us, comfortably inside the ~350k LUT/1900 DSP/1us envelope), so the marginal value of a much-weaker guaranteed-to-fit BDT as "insurance" is far smaller than claimed — the team's actual risk is AUC competitiveness, which this recipe does not insure against. (c) The diagnostic's clean two-way interpretation in step 3 is undermined by step 1 folding candidate aggregates and recipe #5 outputs into the same BDT as the scalars — a low AUC there doesn't cleanly localize the bottleneck as claimed, since it isn't a scalars-only test; needs a separate scalars-only control arm. (d) The proposed 2-hour effort omits real friction (first-time conifer/XGBoost export, xcu200 part config, Vitis HLS run time) and doesn't address that Vitis synthesis is a shared, currently-loaded resource (already running the DeepSet's ap_fixed<16,6> job) with only ~24h left — contention isn't acknowledged. (e) The optional logit-ensemble step cites no evidence that it helps AUC; naively averaging a much weaker model into a strong one is more likely to hurt than help without calibration, which the recipe doesn't flag as a risk. On criterion (4), the diagnostic premise itself (BDT-on-flat-features trailing structure-aware models by far more than 0.002 AUC) is independently well supported by Kasieczka et al., "The Machine Learning Landscape of Top Taggers" (arXiv:1902.09914/SciPost Phys. 7, 014), which reports deep low-level models beating HLF-BDTs by roughly a factor of 2-3 in background rejection — so the diagnostic's basic bet is sound, just not for the reasons or with the citation given, and not with the "insurance"/ensemble add-ons as written.

## Dead ends found by the scouts
- Literal Attention Transfer (Zagoruyko & Komodakis, arXiv:1612.03928) as originally defined operates on CNN spatial feature-map activations — the DeepSet student has no spatial grid, so it cannot be applied as-is; only usable as inspiration for a per-candidate auxiliary regression target (folded into idea #2 above), not as a drop-in loss.
- Contrastive Representation Distillation (CRD, arXiv:1910.10699) requires a memory bank of negative samples and a contrastive/InfoNCE-style setup — its machinery (momentum encoders, negative sampling) is heavier engineering than a few-hour turnaround justifies here; the simpler RKD distance/angle loss (idea #4) captures most of the same 'relational structure' benefit for far less implementation risk.
- Chaining more than one teacher-assistant hop (e.g. ParT -> intermediate -> BigDeepSet -> tiny) is not supported by the TAKD paper itself, which finds a single well-chosen TA is typically sufficient and returns diminish or reverse with too many hops — stick to the one-hop ParT-lite/BigDeepSet -> tiny chain, don't over-engineer a longer chain.
- JetCoRD's full architecture (separate per-experiment domain tokens, dual student/gate heads, cross-experiment reconciliation) is built for merging two incompatible teachers (ATLAS GN2 + CMS ParT) into one deployable student — none of that multi-domain scaffolding applies to a single-teacher, single-domain problem like ours; only its reliability-weight + prototype-repair loss terms are relevant (used narrowly in idea #3), the rest should not be replicated.
- DistillNet's headline '98.9% accuracy' and its FPGA latency/resource numbers are for a regression task (per-particle pileup weight, not signal/background AUC) — cannot be quoted as an expected AUC number for our classifier; only the distillation *pattern* (per-candidate soft targets from a relational teacher into a tiny per-candidate MLP, verified cheap on FPGA via hls4ml) transfers, not the specific performance figure.
- Could not find any published paper distilling a ParT-style transformer specifically into a DeepSet for an L1-trigger-latency FPGA target — the closest matches found (LorentzNet->DeepSet KD in arXiv:2311.14160, and DistillNet's GNN->MLP in arXiv:2311.12551) are strong analogs but neither is literally 'ParT into DeepSet for hls4ml', so no single paper gives a directly transplantable number for our exact architecture pair; treat all AUC-magnitude estimates above as priors from adjacent setups, not guarantees.
- Full multi-head self-attention (MHA) transformer student: arXiv:2510.24784 shows MHA underperforms Linformer at every input length (77.9% vs 79.8% acc at 64 particles) due to its O(n^2) complexity, and hls4ml's attention/transformer support was only contributed in that same very recent paper (immature, largely untested outside its own benchmarks) -- too much toolchain risk to stand up from scratch in <24h even before considering whether the *linear*-attention variant that does win would itself synthesize in budget.
- LUT-native architectures trained from scratch (LogicNets, PolyLUT, NeuraLUT-Assemble, NullaNet): despite excellent published numbers on comparable-scale tasks (e.g. LogicNets FPL'20: 177 LUT/0 DSP/~10ns at 71.8% acc on the HLF-JSC benchmark per HGQ paper's Table 2), these require training in a completely different framework (github.com/Xilinx/logicnets, PolyLUT, NeuraLUT-Assemble) outside the team's current Keras/QKeras/hls4ml workflow, with no straightforward way to inherit the existing 2,041-param checkpoint, the distillation setup, or the event-scalar concat glue code. HGQ+da4ml (ideas 1-2) captures most of the same DSP-free, few-thousand-LUT benefit with a far smaller integration diff onto the existing pipeline -- not worth the framework-switch risk with this little time left.
- Binary/ternary weight quantization of the current DeepSet (arXiv:2003.06308-style): could not extract concrete AUC-vs-resource numbers from the paper (PDF text extraction failed), so this stays unverified. More importantly, at only 2,041 parameters the model's DSP/LUT cost is compute/multiplier-instantiation-bound, not weight-storage-bound, which is the regime binary/ternary compression targets on much larger models; HGQ's own related-work discussion explicitly positions itself as superseding binary/ternary and LUT-based methods once a model is already down to a few thousand LUTs, which is exactly this student's regime -- so this doesn't transfer as a standalone lever here.
- Full O(N^2) Interaction Network as an outright architecture swap (not just a small added edge branch): arXiv:2402.01876 Table 3 shows that at N=16 constituents, with only per-model-uniform 8-bit QKeras quantization (no HGQ), the IN costs 5,362 DSP (43.6% of a VU13P) and 1.39M LUT (80.3%) -- alone this exceeds the entire VU9P challenge budget (1,900 DSP / ~350k LUT) many times over, before even adding the event-scalar branch. Not viable as a full replacement within 24h without a much deeper per-parameter HGQ requantization effort than time allows; kept only as the much smaller 'add one small edge branch' stretch idea instead.
- Separate-phase Masked Particle Modeling (arXiv:2401.13537) or JetCLR contrastive pretraining (arXiv:2108.04253) of the FPGA STUDENT itself — three independent papers (2401.13537 Fig.3, arXiv:2408.09343, arXiv:2606.14870) all show the pretraining advantage concentrates in the low-label-budget regime and the from-scratch supervised model converges to (not past) the pretrained one once labels are abundant. We have 2M labels for a 2,041-parameter model — squarely 'abundant labels, tiny capacity', which is the opposite regime SSL pretraining is shown to help in; the diagnosed bottleneck is architectural (no relational/pairwise term in a mean-pool DeepSet) not label scarcity, and pretraining doesn't add capacity.
- Loading pretrained OmniJet-alpha (arXiv:2403.05618), OmniLearn/OmniLearned (arXiv:2404.16091, 2502.14652, 2510.24066) weights into student or teacher — domain/feature mismatch: their tokenizers and embeddings are built for generic jet constituents with full 4-vectors and often particle-ID, while ours are 16 zero-padded L1 PUPPI candidates with only 5 hand-engineered features (log pt, eta, cosphi, sinphi, dxy). Reusing the embedding layers isn't possible without redesigning the input pipeline, and even a successful adaptation would still be capped by the abundant-label finding above — not worth the adaptation effort inside 24h.
- J-JEPA / HEP-JEPA world-model self-supervision (arXiv:2412.05333, and HEP-JEPA arXiv:2502.03933) — only workshop-abstract-depth material was retrievable in this pass: no quantitative AUC tables, no clear from-scratch training recipe an agent could implement correctly in a few hours. Too much implementation risk this close to the deadline; flag as a genuinely interesting post-hackathon direction, not a same-night one.
- Blind/untargeted point-cloud mixup across all classes without first checking class balance — PointMixup's (arXiv:2008.06374) own evidence is specifically for scarce-example regimes; applying it without confirming ttbar is actually underrepresented in the 2M events risks blurring an already-adequate decision boundary and regressing AUC for no reason.
- Diffusion/flow-matching augmentation of the SIGNAL class rather than the diagnosed-weak ttbar background — the one HEP paper found with quantitative evidence (arXiv:2402.13684) shows the benefit of generator oversampling is reduced statistical uncertainty under a compute-bound-simulation budget, not classifier AUC lift, and signal is not where the model is weak (0.887 vs 0.759 for ttbar) — low expected payoff for the effort.
- Putting the CICADA/AXOL1TL-style autoencoder ON-CHIP as an inference-time input feature (rather than as an offline auxiliary training target) — the student alone already uses 319k LUT / 1724 DSP / 0.39us at ap_fixed<22,10>, close to the one-SLR/1us budget; synthesizing a second network alongside it to compute a live anomaly score is not realistic within the remaining resource and time budget.
- Full O(N^2) Interaction Network as the deployed student: per arXiv:2402.01876's own controlled comparison at 16 constituents, IN only edges out DeepSets by ~1.4 accuracy points (70.8% vs 69.4%, different 5-class benchmark, not our HH4b task) while costing ~3.5x the DSPs and more LUT/FF/latency than DeepSets at N=8 (472k LUT/2191 DSP/160ns vs 386k LUT/626 DSP/95ns) — with our student already at 319k LUT on a ~350k-LUT one-SLR budget, a full IN would very likely blow the resource/latency envelope for a small, unproven AUC gain. JEDI-linear (idea 1) is a strict resource-cost improvement over this path that recovers most of the same relational benefit, so plain IN is superseded, not just risky.
- Deploying the ParT-lite (or any full self-attention transformer) architecture as the FPGA student: web search results explicitly characterize state-of-the-art attention architectures' latency/resource consumption as 'incompatible with L1T constraints' even in papers specifically chasing sub-microsecond transformers (arXiv:2510.24784); use ParT-lite only as an off-FPGA teacher (as already planned), not as a synthesis target.
- Copying WOMBAT's (arXiv:2505.05532) PID-class input features (electron/muon flags) to help ttbar rejection: WOMBAT's biggest per-class gains are for lepton PID classes, which is exactly a ttbar-vs-HH4b handle (HH4b has no prompt leptons), but our challenge's frozen 5 features/candidate (log pt, eta, cos phi, sin phi, dxy) contain no PID/charge information, so this doesn't transfer unless the underlying ntuple secretly carries a PID field outside the stated 5 — worth a 10-minute check of the raw data schema, but not assumable, so not built into a full idea here.
- Pulling exact AUC/loss numbers from arXiv:2311.14160 (distillation) and arXiv:2308.05170 (pruning) PDFs: both PDF fetches returned corrupted/undecodable binary streams via the fetch tool, so only abstract-level claims could be verified for idea 5; the mechanism/precedent is solid but the specific magnitude numbers cited in the idea are not independently confirmed and should be pulled from the actual paper text before over-trusting the delta.
- Full end-to-end symbolic regression (PySR or SymbolNet) directly on all 91 raw student inputs (16 candidates x 5 features + 11 scalars): SymbolNet's own paper (arXiv:2401.09949) needed a whole adaptive-pruning training framework just to handle 16 scalar inputs and still lost 4 accuracy points vs the NN baseline; scaling that search to 91 raw, largely-redundant per-candidate inputs is very unlikely to converge to a useful expression within a few agent-hours -- point symbolic regression at engineered/pooled features instead (see ideas above), not raw inputs.
- High-degree (d>4) Energy Flow Polynomials: the complete linear EFP basis grows combinatorially with degree; even the original offline study (arXiv:1712.07124) needed pruning to stay tractable past d~7. At 200MHz/1us/1-SLR with pairwise terms already competing for DSPs, anything beyond d=2-3 EFPs is not FPGA-appropriate for this challenge.
- Schmidt & Lipson's original 'Distilling Free-Form Natural Laws from Experimental Data' (2009, Science) as a direct source: it's the foundational symbolic-regression paper but predates PySR/hls4ml tooling and has no HEP or FPGA-resource evidence attached -- useful as background only, not as a citable transfer of numbers to our budget.
- Deploying a literal (even shrunk) attention/transformer block on the FPGA instead of distilling it away: FPGA-transformer papers (e.g. arXiv:2409.05207, Low Latency Transformer Inference on FPGAs with hls4ml) show attention is inherently more DSP/LUT-hungry per parameter than dense/DeepSet layers even after quantization; this contradicts the challenge's own current strategy (a 2k-param DeepSet) and the 1-SLR target, so it's out of scope for the 'interpretable distillation' lens even if technically synthesizable.
- Treating ParT-lite's pairwise attention as a smooth function of (ln dR, ln kT, ln z, ln m2) that a single closed-form PySR fit can capture wholesale: arXiv:2512.00210 found ParT's learned attention maps are sparse and nearly binary (each particle effectively attends to <=1 other particle) rather than a smooth kernel over the 4 kinematic features, and that zeroing the kinematic bias alone collapses accuracy from 0.861 to 0.405 -- so neither 'ignore the bias' nor 'assume it's smooth and globally fittable' is well-supported; the argmin/nearest-neighbor approximation (idea 2) is the better-supported middle ground.
